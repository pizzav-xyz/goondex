The effective interval is the max of client and proxy spacing for that source. Fix the README's "2 req/s" claim: it describes only one of two limiters, and 2 req/s is wrong for both sources anyway.

## 5. e621 Adapter

- [x] 5.1 Create `src/sources/e621/normalize.ts` mapping the e621 wire format to the canonical `Post` (Verified 2026-10-01, e621ng@9ecbb7e + live):
  - `tags` object of 9 category arrays → flat array. The keys are EXACTLY `general, artist, contributor, copyright, character, species, invalid, meta, lore`. The key is `meta`, not `metatag`, and `contributor` is real and easily missed; both must be flattened.
  - Timestamps: `created_at` and `updated_at` are ISO 8601 with milliseconds and a SERVER-LOCAL offset (`2026-10-01T13:44:40.176-04:00`, `-05:00` on older posts). Parse offset-aware and never assume UTC — the docs' literal `+00:00` is wrong.
  - URLs: `file.url`, `preview.url`, `sample.url`. `sample.has` exists but is NOT a safe guard: the `sample.url` key is always present with value `null` when absent, even under `has: true` when the file is gone, and `sample.width`/`height` stay populated even when `has: false`. Guard on the TRUTHINESS of `url` (or on `has`), never on key presence. `file.url` and `preview.url` are likewise nullable (pending/deleted posts; ~40% of anonymous results carry `flags.pending = true`). Also carry `alt` (nullable webp URL) and `sample.alternates` (video `original`/`variants` webm+mp4, `samples` 480p+720p) — a webm post usually exposes an mp4 alternate and vice versa, so prefer the mp4 alternate.
  - `score` is EXACTLY `{up, down, total}` and `down` CAN be negative; do not assume a sign. Use `total`.
  - `sources` is an ARRAY OF STRINGS, always a list, possibly `[]`. There is NO singular `source` field. Treat entries as untrusted free text.
  - Rating: server-side single-character `s`/`q`/`e` → canonical scale.
  - uploader/status: there is NO top-level `status`, `is_pending`, `creator_id`, or `creator_name`. Canonical `Post` must use e621's actual names: `uploader_id`, `uploader_name`, `approver_id`, and `flags` as 6 booleans (pending, flagged, note_locked, status_locked, rating_locked, deleted).
  - `duration` is a top-level FLOAT in seconds (`0.999983`, `674.377143`) — parse as float, never int — and is `null` on non-video posts (not 0, not absent). Prefer it; fall back to client-side probing only when null.
  - File extension: read e621's dedicated `file.ext` field, falling back to the `file.url` path only if absent. (Rule34 is the board with no extension field — it derives from `image`.)
- [x] 5.2 Create `src/sources/e621/index.ts`: `posts.json` search, `tags.json?search[name_matches]=` completion, `GET /posts/<id>.json` post detail, `maxPageSize: 320`, permitted hosts `static1.e621.net` and `static1.e926.net`, `videoExtensions: ['webm','mp4']` (mp4-dominant ~73% + webm ~27%; `gif` is additionally treated as video-capable alongside the array, not inside it — the array holds container codecs for extension detection, and gif is matched as video-capable by the shared helpers), **native date filter support**, auth via HTTP Basic ONLY (single code path: `Authorization: Basic base64(login:api_key)`). There is deliberately no `login`+`api_key` query-param fallback — the proxy always sets headers, so the fallback's documented use case (clients that cannot set headers) never occurs, and two auth paths for one personal client is exactly the duplicated fallback Rule 1 forbids. Credentials come from new `E621_LOGIN` / `E621_API_KEY` env vars (anonymous reads stay supported and are the default when unset).
  - Completion is `name_matches`-ONLY, with `*` wildcards working anywhere (`smile*`, `*`, case-insensitive). `search[prefix]`, `search[name_prefix]`, and `search[starts_with]` do not exist and are silently ignored, which yields unfiltered defaults instead of an error. Ratings are metatags, not tag rows, so `tags.json?search[name]=rating:e` returns `[]`.
  - `tags.json` returns a BARE TOP-LEVEL ARRAY on success but `{"tags":[]}` on zero results; handle both shapes.
  - Pagination: `page` is hard-capped at 750, so bulk traversal uses the cursor forms `page=a<id>` / `page=b<id>`. `limit=0` returns a 200 with an empty page.
- [x] 5.3 Always send an explicit `limit` on every e621 posts.json request. The default page size is 75, so relying on the default silently truncates every page. Clamp the caller's value to the `maxPageSize: 320` cap.
  - Handle the over-limit case as a distinct response: e621 returns **HTTP 410 Gone** with `{"success":false,"message":"Limit must be between 0 and 320.","code":null}` when `limit` exceeds 320. This is the OPPOSITE of Rule34, which silently clamps at HTTP 200 with no error and no truncation signal. A 410 on `limit` is a client-side clamp bug, not a source outage or a rate-limit condition, and must be classified as such.
- [x] 5.4 Pin the request and response shape to the LEGACY JSON form, which is the default: wrapped `{"posts":[...]}` for search and `{"post":{...}}` for detail. NEVER send `v2=true`: it reshapes the response (`tags` becomes a FLAT ARRAY in basic mode, and fields move under `files`/`stats`), which would silently break the normalizer. Add a test that asserts `v2` is absent from the outgoing query on every posts.json and tags.json request.
  - Detail routing: `GET /posts/<id>.json` → `{"post":{...}}` is the canonical route; `tags=id:<n>` also works inside posts.json; `search[id]=` does NOT filter; `/post/<id>.json` (singular) is a 404. - [x] 5.5 Add a `date:` pass-through path in `SearchView` for sources declaring native date support, so the term reaches e621 unchanged instead of going through rate-sampling. This task is wiring ONLY: grammar validation lives exclusively in the shared normalizer (10.4) — no validation logic here, no second copy of the grammar. ## 7. Date Filtering Correctness (Rule34)

- [x] 7.1 Collapse the `resolve → calibrate → resolve` fallback chain into a single `threshold_for(days)` that owns rate estimation internally and returns an explicit "no threshold" result. The chain is real, but `calibrate(days_list)` is NOT dead code: it is called with `[days]`, so align its signature with that usage rather than deleting the parameter. The current `except Exception: pass` looks like a bare pass but actually LOGS, and that is not the worst of it: on failure the date tag is stripped and the search proceeds UNFILTERED with no notice to the user. Collapse the chain so the single `threshold_for` reports failure instead.
- [x] 7.2 Make the caller report an unresolvable date filter instead of silently issuing a broader search. On Rule34 a date filter that cannot be resolved surfaces as an EMPTY result set, never as too many results, because Rule34 has no date operator at all: `date:week`/`date:month`/`date:year`/`date:2024`/`date:>...`, `created_at:>`, `change:>`, and `age:` ALL return zero posts, and any unknown qualified tag zeroes the result set rather than being ignored or erroring.
- [x] 7.3 Replace `matches[-1]` last-wins date extraction with narrowest-constraint-wins, and inform the user how multiple date terms were resolved.
- [x] 7.4 Extend the date-term grammar to accept BOTH singular and plural units (`date:30day` and `date:30days` are equivalent), and reject unrecognized date syntax outright instead of letting it fall through as an ordinary tag — a fall-through date tag is then sent upstream and zeroes the Rule34 result set.
- [x] 7.5 Add a verification requirement that a native-date source's results are confirmed to fall within the requested range, so a source that silently ignores `date:` is caught rather than trusted.
- [x] 7.6 Document the full e621 `date:` grammar as the reference for validating pass-through terms: units second/minute/hour/day/week/month/year with singular and plural forms; abbreviations s/mi/h/d/w/mo/y; a bare NUMBER meaning DAYS (`date:30` = 30 days ago); `_ago`/`ago` suffixes; bare `day`/`week`/`month`/`year` (= 1 unit ago, while bare `second`/`minute`/`hour` REQUIRE a number); keywords `today`/`yesterday`/`decade`; `yesterweek`/`yestermonth`/`yesteryear` with counts; absolute dates (`date:2024-01-01`, `april/27/2012`); comparisons `>`/`<`/`>=`/`<=`; inclusive `..` ranges (`a..b`, `..b`, `a..`); and comma lists capped at 320. Relative forms emit a LOWER BOUND (`>= now-N`); a bare absolute date is a single-day exact match. Explicitly flag the two traps: never emit a bare year (it means that many days ago), and bare `hour`/`minute`/`second` are invalid.
- [ ] 7.7 Document that Rule34 requires DEEP PAGINATION for date windows instead of a server-side date filter. `change` is an integer of UNIX SECONDS but it is LAST-MODIFIED time, not creation time — Rule34 exposes NO creation timestamp of any kind (`created_at` does not exist) — so week/month/year windows must be resolved by paging an id-sampled threshold client-side. `page=` is not a valid pagination param (`page` BREAKS the query: HTTP 200 with a 0-byte body); the real param is 0-based `pid=`.

- [x] 10.2 Implement the rating translation. - [ ] 11.8 Wire-trap verifications against the live APIs and captured fixtures, each asserting the specific failure mode rather than just a non-crash:
  - 410-vs-clamp asymmetry: Rule34 with `limit=2000` returns HTTP 200 with a byte-identical 1000-post page and no truncation signal, while e621 with `limit` above 320 returns HTTP 410 with `{"success":false,"message":"Limit must be between 0 and 320.","code":null}`. Assert both are classified differently and that the Rule34 side clamps client-side.
  - 0-byte body: a Rule34 query with zero results returns HTTP 200 with a 0-BYTE body, never `[]`, so an unguarded `json.loads()` throws. Same for nonexistent tags and for the broken `page=` param. Assert empty results are handled without a parse error.
  - JSON-string auth error: an anonymous Rule34 request returns HTTP 200 whose body is a bare JSON STRING (`"Missing authentication. Go to api.rule34.xxx for more information"`), not an array. Assert auth failure is detected by body TYPE, never by status code, and that a bad or empty key returns full data identically to a valid one.
  - Null-URL tolerance: an e621 post with `sample.has: true` but `sample.url: null` (file gone) must render without a broken image, as must null `file.url`/`preview.url` on pending or deleted posts. Guard on truthiness, not key presence. Also confirm `sample.width`/`height` are populated under `has: false` and are not treated as a has-sample signal.
  - 429+503 handling: Rule34 429s with an empty body and no `Retry-After`; e621 429s with an HTML body and `Retry-After: 2`, and the docs also name 503. Assert 429 and 503 are both classified as rate-limit, that neither body is blind-parsed as JSON, and that the absent `Retry-After` falls back to our own backoff timer.
  - Legacy-shape assertion: assert `v2` is absent from every outgoing e621 request and that responses are unwrapped from `{"posts":[...]}` / `{"post":{...}}`. Assert the detail route is `/posts/<id>.json` and that the singular `/post/<id>.json` is not used.
  - Explicit-limit assertion: assert every e621 posts.json request carries an explicit `limit` (never relying on the default 75) and that the value never exceeds 320.
  - Rating spelling assertions: Rule34 requests contain only `rating:explicit`/`rating:questionable` and no short forms; e621 requests contain only `rating:s`/`rating:q`/`rating:e` and no long forms; an unrecognized rating is rejected client-side rather than forwarded.
  - Date-trap assertions: bare `date:2024` is rejected or never emitted (it means 2024 days ago); bare `hour`/`minute`/`second` are rejected as invalid; an invalid date is rejected client-side rather than sent to produce an HTTP 422; and plural input is accepted and canonicalised. On the Rule34 side, assert `date:` never reaches the wire and that the resolver's threshold path deep-paginates with `pid=`, treating `change` as last-modified rather than creation time.
  - Ordering assertions: on Rule34 a `sort:` request produces a user-visible drop notice and no ordering parameter on the wire; on e621 the emitted parameter is `order:` with the underscore suffix form (`order:id_asc`, `order:score_asc`) and never the space or colon forms, which silently return zero. Additionally verify LIVE that `order:created_desc`/`order:created_asc` actually honor creation order (check the `created_at` sequence across the returned page): the mapping `sort:date` → `order:created_desc` was derived from source reading, never from a live ordering check, and must not ship unverified.
  - Autocomplete assertions: Rule34 completion is parsed despite the `text/html` content type and the parenthesized count is stripped from labels; e621 completion sends `search[name_matches]=` with wildcards and never `search[prefix]`/`search[name_prefix]`/`search[starts_with]`; both the bare-array and `{"tags":[]}` zero-result shapes are handled.
  - CSP host assertions: the explicit `img-src`/`media-src` list includes `api-cdn.rule34.xxx`, `api-cdn-mp4.rule34.xxx`, `static1.e621.net`, and `static1.e926.net`, a video post actually loads on the mp4 host, and the registry-coverage test from 8.6 passes.
